# Agent Workbench

## Purpose

Give the owner one understandable website for reviewing proposed actions, checking personal context and coverage, following runs and opening the same professional business records.

## ADDED Requirements

### Requirement: Business data before autonomous operation
The system SHALL prioritize the owner's usable requirements/matters pool and business input/output with a shared scoped API/Skill before the website Agent. It SHALL preserve the original public requirement identities and keep private new/overlay data in the same authorized projection without promoting edits to engineering completion or acceptance.

#### Scenario: Add or edit a private requirement
- **WHEN** the authorized owner saves new text or a baseline-bound edit
- **THEN** the existing writer persists source/history and an idempotent versioned result, the website reads it back, and the matching Agent operation uses explicit requirement scopes
- **AND** stale baselines, concurrent duplicate overlays, foreign owners, removed grants and uncertain results cannot silently overwrite or duplicate data
- **AND** missing activation remains explicit and does not prevent independent already-authorized source work

### Requirement: Every delivery slice exposes usable website value

Each released slice SHALL include an operable website path, honest connection/availability state, version identity and a real readback path. API-only source work, document visibility or internal synthetic previews SHALL NOT be described as completed owner delivery.

#### Scenario: Real source activation is not authorized

- **WHEN** code is qualified but a source or runtime activation package is missing
- **THEN** the website exposes usable coverage or authorization controls and clearly marks the dependent end-to-end acceptance as incomplete

### Requirement: Workbench exposes evidence and review without noise

The workbench SHALL provide focused review, confirmed-context/coverage, run-progress and insight destinations. Proposal detail SHALL show its source basis, differences, uncertainty and current status, allowing correction, rejection or deferral without pretending an inference is a fact.

#### Scenario: Owner opens an insight with incomplete evidence

- **WHEN** the insight depends on partial or stale source coverage
- **THEN** the website shows that limitation and the referenced evidence before offering an optional action

### Requirement: Professional views share entity identity and writers

Task/project, journal/people, calendar, health and finance views SHALL retain their typed domain semantics and open the same entity and revision from the workbench. Missing source fields or unsupported modules MUST NOT be replaced with invented data or a separate generic writer.

#### Scenario: Owner opens a classified task from review

- **WHEN** the owner follows a result into the task view
- **THEN** the view reads the same persisted task identity, relations and version used by the receipt

### Requirement: Mobile review preserves drafts and uncertain commands

The website SHALL support keyboard/focus and readable light/dark layouts from360px, preserving existing navigation and draft guards. Busy or uncertain actions SHALL retain their exact command and recovery path across dialogs, refresh and supported re-entry.

#### Scenario: Closing a dialog during an uncertain commit

- **WHEN** a commit has an unknown outcome
- **THEN** the website protects the original request and offers receipt/readback recovery rather than generating a new command

### Requirement: Delivery evidence remains separate from acceptance

The system SHALL distinguish source implementation, executed tests, deployment/readback and owner experience acceptance. Existing requirement IDs, unresolved gates and explicit pauses SHALL survive new slices; the original UI task completion state MUST NOT be increased by this parent plan.

#### Scenario: A new Agent slice passes source tests

- **WHEN** source checks pass while runtime or owner acceptance remains unavailable
- **THEN** the roadmap preserves those outstanding gates rather than presenting the entire requirement as accepted

### Requirement: Existing matter workflows remain executable requirements

The workbench SHALL retain the original task Kanban, newline batch entry, reversible deletion and matter-Gantt requirements with their original IDs and delivery gates. Matter Gantt SHALL use real task identities and explicit date semantics, including undated items; the requirements-roadmap Gantt MUST NOT substitute for it.

#### Scenario: A task has no start or end date

- **WHEN** the owner opens the matter Gantt
- **THEN** that task remains visible as undated and no interval is invented from its title or due date

### Requirement: Relationship exploration uses explicit evidence

Relationship graph delivery SHALL include interactive exploration of explicit authorized links, edge counts, time/type filters and source drilldown through a qualified mature renderer. Execution graphs, JSON exports and inferred co-occurrence MUST NOT be presented as the completed relationship graph.

#### Scenario: Owner filters the relationship graph by time

- **WHEN** the owner selects a time range
- **THEN** visible edge counts match their accessible contributing records and open those records as evidence, with unknown-date coverage identified
