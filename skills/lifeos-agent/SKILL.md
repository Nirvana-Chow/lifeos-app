## Owner-reviewed todo classification

`previewTodoClassification` requires `todo:read` and `organization:read`, without business write permission. Send `{changes}` with 1–100 distinct todos. Each change is `{todo:{id,sourceId,expectedRevision},before,after}`. Both relations objects contain `project`, `domain`, and `topics`; `before` may be `null`. Reference objects contain the current `{id,sourceId,revision}`. Topics are ordered with at most 20 entries. The entire body is limited to 128KiB. Use exact readback values; do not send titles, notes, status, dates, owner, space, actor, source evidence, or extra fields. A preview saves only an immutable plan with a digest and 30-minute expiry, never business records.

Read the complete todo and organization snapshots before suggesting classifications. If a new project, domain, or topic is needed, propose it first; create it only with specific authorization and read it back before using its real reference. Share the fixed owner review link `/personal?modal=classification&planId=<planId>` on the same approved website origin. Have the owner review the fixed plan at the website. Approval requires the current owner MFA session and creates a server receipt; no Agent/MCP approval operation exists. `confirmed:true`, model output, or a run checkpoint cannot replace owner approval. The owner may select a subset before approval; it creates a separate plan with the original expiry only if the entire base remains current. Old and new plans are independent, and a new plan does not revoke any existing approval. Selection is locked after approval or while an outcome is unknown. Adjusting any difference or selection requires a new preview and approval.

`commitTodoClassification` additionally requires `todo:write`. Call API commit only when that operation is separately advertised and the owner approval is stored. If commit is not advertised, hand the proposal to the owner website; do not attempt API commit or request broader grant scopes just to enable this path. Send `{planId,digest,confirmed:true}` with a unique `Idempotency-Key`, using the approved preview unchanged. The owner's website can commit a read-only producer's plan using the owner's own write authority while the producer's original read grant remains valid. Approval does not expand that grant. A background run cannot approve or commit.

The result contains `planId`, `digest`, `duplicate`, `entries` (ID, source ID, revision, personal relations) and `unchangedIds`. The whole batch succeeds or fails together; no-op entries retain their revision. Read each affected todo individually and compare source ID, revision and personal relations with the receipt; report later changes or unreadable records without overwriting them. A plan is consumed once even if all entries are unchanged. On an unknown outcome, preserve the exact original key/body and retry only those; authorized replay returns the historical receipt even after expiry or later edits. A different key is not recovery. On conflict, stop and create a new reviewed preview only after rereading the changed records. Revoked producer or current actor authority blocks both commit and receipt recovery.

Old explicit grants do not gain them. Source support is not SQL registration, runtime activation or installed-host qualification.

Never rescan, fabricate paths/decisions or upload private data to public sources as part of intake.

`updateStorageReviewChecklist` uses the actual record ID, expectedRevision and `{fields:{checklist}}`. A new checklist revision preserves decisions only for unchanged objects with the same IDs; changing/removing a decided object conflicts. Reread and resolve it explicitly; never reset decisions or invent replacement IDs to bypass the conflict.

`updateStorageReviewDecision` uses the record ID and expectedRevision with `{fields:{checklistRevision,itemId,decision}}`; decision is `keep`, `trash`, `defer` or null to clear that item's choice. Only pending items may change. This is an ordinary recorded choice, not evidence that the owner personally approved it, and not file deletion authorization. Agent-origin commands retain server-derived grant/operation audit; never send owner/source/actor fields.

Every write needs its original idempotency key and an independent `getStorageReview` readback. Keep/defer/protected/processed entries do not authorize deletion.

## Persistent requirements

For actionable feature requests, bug reports, accepted ideas or corrections from any chat, use the workflow below to enter the same owner requirement pool. Discussion, diary facts and a question alone do not create execution work. The owner can refine a request while implementation continues; a new chat is not a new backlog.

1. Read the complete requirement snapshot, then individually get likely matching stable IDs. Deduplicate by the requested behavior, trigger and outcome, not just title similarity. Extend a matching requirement with the new source, constraints and acceptance; do not create one row per spoken fragment or remove earlier unfinished work. Create a private requirement only when no matching behavior exists. If a complete inventory cannot be read, preserve the pending input and report that intake is unconfirmed rather than guessing there are no matches.
2. Keep the owner's request distinct from the Agent's interpretation, recommended approach and weak ideas. In the editable body, concisely retain the authorized source chat/date, requested outcome, acceptance, dependencies and explicit holds/cancellations. These are business text, not forged immutable source/evidence fields. Do not copy private chat text into public Issues or source baselines. Preserve actual phase IDs and unrelated fields from reads; keep unknown dates null. Do not silently discard an explicit request because the Agent judges it low value; record a recommendation separately. A suggestion without a clear request can remain a candidate instead of automatically starting work.
3. Write each distinct change with its own original idempotency key, then independently get the same stable ID. Compare complete fields, source identity, revision and baseline binding. Report saved IDs only after successful readback. On conflict reread and reconcile the owner's additions with the current record; on an unknown outcome recover the original command. Never truncate existing acceptance or overwrite a newer edit to make intake succeed.
4. Continue the already authorized delivery workflow after confirmed intake; ordinary refinement does not require another per-feature permission question. Map the stable requirement to its existing engineering Issue/OpenSpec tasks without substituting code documents for the business record. Preserve cancelled/paused work and separate implementation, CI, deployment and owner acceptance. A proposed change or successful save is not owner experience acceptance. Missing API/runtime authority leaves a visible pending intake and does not block independent already authorized work or repairing the access path.
5. Automatic execution requires a separately qualified advertised event/claim interface and native worker channel. Saving a requirement does not prove it was dispatched or a worker started. Prefer server events with durable cursor replay, claim/renew/fencing and bounded capacity; do not run repeated model calls to discover an empty queue. Resume offline events through the qualified listener, not by creating duplicate requirements or bypassing a lease. A generic owner-write credential is not a lease-restricted worker delegation.

Use requirement operations only when advertised by v2 discovery with explicit `requirements:read` / `requirements:write` scopes. Todo/organization permissions do not authorize requirement access, and old issuer modes cannot grant these scopes. Owner CRUD can be available while Agent requirements remain closed.

`snapshotRequirements` returns the complete server-composed public baseline plus the current owner's private requirements. IDs are stable public `LO-…` IDs or private UUIDs. `getRequirement` returns `{entry}` with complete `fields`, `revision`, `baselineBinding` and `baselineConflict`. The six required fields are `title`, `body`, `phaseId`, `priority` (`P0`–`P3`), `plannedStartOn` and `plannedEndOn`; `workflow` is optional. Read available phase IDs from the snapshot baseline. Dates are actual ISO calendar dates or null; never invent schedule dates. Text body is limited to16384 characters and the entire request to128KiB.

`createRequirement` accepts `{fields}`. `updateRequirement` accepts `{fields,expectedRevision,baselineBinding}` with all six required fields, optional `workflow` and the exact binding returned by the current read; private requirements use null. A public row with no private overlay has revision0. First edit creates one owner/space/public-ID overlay rather than another public row. Evidence, source and user acceptance are immutable through this API; never include those fields or infer acceptance from a successful edit. Public baseline version/item version/digest changes return a baseline conflict; preserve the draft and reread instead of rebinding or overwriting automatically. A visible `baselineConflict` also needs review before a new edit.

Owner business purposes, descriptions, priorities, phases, dates and progress belong in these records. Update them with the advertised scoped API and independent readback; do not edit source baselines, redeploy, use direct SQL or administrative credentials for routine business-data changes. Missing authority blocks the affected data write.

Optional `workflow` is `{state,purpose,nextStep}` or `null`. State is exactly `planned`, `in_progress`, `blocked`, `awaiting_review` or `done`; purpose and nextStep are literal strings up to4096 characters each, including empty strings. Send a complete workflow object when changing it. Omit `workflow` on an update to preserve the existing value; explicitly send null to clear it. Existing six-field commands and records remain valid. These are owner business labels: `done` does not mean verified implementation, deployment, CI or owner acceptance. None of those authority fields can be edited through this API. Do not invent descriptions, purpose, status, next actions or completion evidence; read actual content and record the owner-authorized change.

Writes require the same idempotency/readback rules above. On unknown outcomes preserve and retry only the exact original body/key, then get the same ID and compare returned fields/revision. A replay can return a historical receipt when later edits occurred; report the current read separately. Private descriptions remain in the owner PostgreSQL store and are never automatically published to public GitHub Issues or source.

## Personal records and Agent feedback

These operations require the explicit `all-personal-business-v1` policy, their own advertised scopes and enabled native modules. A legacy todo, organization or requirements credential never authorizes them. The portable document does not replace an installed executable credential runtime; a runtime that only permits todo operations must report these operations unavailable until separately reviewed and authorized. Do not change a key, issuer, schema or runtime allowlist to work around missing capability.

Record types in `/v1/records/<type>` are exactly `journal`, `calendar`, `health`, `person`, `finance`, `media`, `career`, `portfolio` and `cooking`. Each has its own snapshot/get/create/update operation and `<type>:read` / `<type>:write` scopes. Match the exact ID/path/scopes from v2 discovery to the operation reference. Snapshot is complete or fails; do not substitute a bounded list. GET an individual ID before PATCH. Native sources remain authoritative; this API does not import Apple Calendar, Contacts, Xunji or a finance ledger.

For journal, calendar, health, person, media, career, portfolio and cooking records, create with `{fields}` and update with `{fields,expectedRevision}`. All four fields are required in both cases: `title`, `text`, `occurredOn` and `personal`. Unknown journal metadata is explicitly `personal:null`; preserve existing metadata on edits. Calendar metadata uses the native schedule/time-zone contract. Health metadata supports manual body, sleep and training records, with explicit original units, time zones, null missing values and planned/completed state. Person metadata preserves explicit aliases/contact details and birthday date or month/day without inferring birth year or relationships. Read and preserve the full native typed metadata; never substitute a partial object. Relations require current `{id,sourceId,revision}` pins read from authorized records. Do not invent IDs, source IDs, dates, units, completion or personal facts. Cross-owner, source and revision conflicts fail closed.

Finance uses the validated native `FinanceDraft` contract, not journal fields: preserve the complete fields returned by its get operation. Amounts are integer minor units with explicit currency; refund, transfer and repayment keep their distinct meanings and required original/account fields. A transaction total is not an account balance. Do not fabricate a balance, convert between units silently, import a ledger or change the finance authority. Create with `{fields}` and update with `{fields,expectedRevision}`; the native writer enforces source ownership, revision checks and refund rules.

Feedback uses `/v1/feedback/snapshot`, `/v1/feedback/{id}` and POST `/v1/feedback`, with separate `feedback:read` / `feedback:write` scopes. Create with `{fields:{text,title?,sourceLabel?}}`; the server assigns `agent-feedback` as the channel. This creates feedback only. It neither accepts nor approves a requirement, converts feedback, archives it or marks a release read. Read the new feedback ID independently and compare its text, channel, source ID and revision with the receipt.

For every write use a fresh `Idempotency-Key`, then independently get the returned ID and compare fields, source identity and revision. Unknown outcomes retain the exact original body/key; replay may return a historical receipt, so compare the current read separately. Authorization or readiness loss blocks reads, writes and receipt recovery. Never broaden permissions or send owner, space, actor, source evidence or confirmation fields in request JSON.


## Media, career and portfolio records

Use these operations only after exact v2 discovery; the three native module gates remain independent and default closed. The reviewed all-business policy does not activate a missing module, SQL operation or executable credential runtime. All three use the four-field personal-record envelope above, native owner/space/source checks, CAS, original idempotency keys and independent GET readback.

`media` metadata has `type:'media'`, `schemaVersion:1`, `mediaKind` (`book`, `film`, `series`), explicit `state` (`wish`, `in_progress`, `completed`, `paused`), creators, optional valid ISBN for books, `external:{provider,id,url}`, explicit started/finished dates, optional0–10 rating, `progress:{current,total,unit}`, and project/domain/topic `links`. Providers are manual, Open Library, TMDB, IMDb or Douban, with platform-specific identifiers/URLs validated for the selected kind. Keep zero progress/rating distinct from null unknown values. Never infer completion or a finish date from progress, metadata or a title match. External metadata adapters are pure input adapters only; this delivery does not enable an external fetch, synchronization, search account or licensed provider connection.

`career` metadata has `type:'career'`, `schemaVersion:1`, `source:{kind:'manual',label,url}`, project/domain/topic links and a strict `careerKind`: education, employment, achievement, resume or opportunity. Education/employment periods retain the known `YYYY`, `YYYY-MM` or full-date precision and explicit unknown/current/ended state. Fact records preserve original text, entered highlights and source/evidence links. Resumes contain a target role and pinned fact IDs; opportunities contain company/role/direction, explicit application state, next step/date and requirement-to-fact/gap/action mappings. Resume facts, opportunity requirement facts and career evidence references may target only same-owner current education/employment/achievement records. The server derives and checks this subtype constraint after locking; never send a client constraint or use another resume/opportunity as evidence. A saved experience is entered material, not verified employment, qualification, skill mastery or permission to send an application. Preserve missing facts and gaps; do not invent achievements or dates.

`portfolio` metadata has `type:'portfolio'`, `schemaVersion:1`, explicit currency, project/domain/topic links and `portfolioKind`: account, asset or investment. Accounts preserve account type and `{balanceMinor,asOf}`; assets preserve asset type and `{valuationMinor,valuationOn,account}`; investments preserve symbol/name, decimal-string quantity, exact `{costMinor,valuationMinor,asOf}` and optional account/asset pins. Amounts are exact integer minor-unit strings; null means unknown and zero remains zero. Monetary values need their actual as-of/valuation date. Keep currencies separate; do not guess exchange rates, current prices, balances or return. Portfolio account references must point to portfolio account records, and asset references to portfolio asset records; the shared transaction verifies subtype, owner, source ID and current revision after locking. These are manual dated account/asset/investment records, separate from finance transactions; no bank/broker connection, trading, payment, automatic valuation or reconciliation is enabled.

## Cooking records

Use `snapshotCooking` and `getCooking` only when advertised for the current grant with `cooking:read`. Creating or updating also requires `cooking:write`. Use the four required fields above. `title` is the dish cooked, `text` is the owner's notes (an empty string is valid), and `occurredOn` is the explicit date cooked as YYYY-MM-DD. Ask for the date when it is unknown. `personal` is `{type:"cooking",schemaVersion:1,recipe:null}` for a manually named dish, or set `recipe` to the exact `{id,sourceUrl}` pair from the LifeOS catalog. Preserve a saved pin during unrelated edits. The API records completed cooking when the owner explicitly says it happened. Photo attachments have a separate storage path and are absent from the cooking operation schema. Confirm by GET of the returned ID.
