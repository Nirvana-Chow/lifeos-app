# Credential runtime

Install this Skill directory with its references in your agent's supported Skill location. Sharing this package shares instructions only. Use an already-qualified API Key runtime or OAuth MCP connection for the intended service. A directory existing, a package being installed, this invocation loading its reviewed instructions and an actual authorized call succeeding are separate observations; report each accurately. This package installs no connection, runtime or host setting and never replaces local restrictions.

For the API Key path, the account owner signs in to their own LifeOS instance, completes its required verification and issues a least-privilege key in Settings → API keys. Configure the exact approved HTTPS origin, API base `/api/platform/agent` and a credential-store reference in the local runtime. A store reference is not the key. Keep account-specific configuration outside the Skill package and Git. Prefer the operating system credential store or the agent platform's documented secret input; do not paste keys into chat, shell arguments, URLs, environment dumps, code or shared files. Do not share a configured credential with another user.

The credential reader must send the key only in the Authorization header, reject redirects, use normal TLS validation, disable persistent cookie/cache storage, bound responses and avoid logging headers or secret values. A downloaded Skill is not an executable credential reader and does not grant access by itself. If no approved runtime is available, explain the missing setup instead of extracting secrets or falling back to browser cookies.

For this service's OAuth path, the qualified host connects to `https://lifeos.nirvanachow.com/api/platform/mcp` using OAuth/CIMD. The owner completes the existing LifeOS password/MFA login and scope consent; do not ask for an API Key, export one, collect login secrets or substitute browser cookies. The host handles the signed login continuation, token exchange, refresh and revocation. Approved `offline_access` permits refresh of this connection; it does not extend the original grant's expiry, add scopes or enable a business operation. Source support and this document do not prove that the endpoint is activated or the host/account supports installation.

OAuth permissions remain the intersection of current token, client, consent, binding, original reviewed grant, current owner identity/MFA factor, server readiness/business policy and user authorization. A current browser MFA session is required for initial code/continue/consent; ordinary website logout or its 30-minute session expiry leaves an independent OAuth delegation active. Revoking the connection/consent, disabling the client, revoking or narrowing the original grant, its expiry, or owner identity/MFA loss must prevent the corresponding access immediately. Password/security reset also invalidates the delegation. A local disconnect label alone is not proof of server revocation. No Key is changed by connecting, refreshing or disconnecting OAuth.

Read requests and conversation do not imply a save. Execute an explicit save/update request under its existing authorization, retain the original command/body/idempotency key and independently GET the same resulting ID to compare fields, source identity and revision. OAuth refresh or reconnect is not write recovery: an unknown outcome never authorizes a new key, changed body, automatic replay or transport fallback. Follow the already-qualified original-command recovery contract below; do not add another owner approval step just because the transport is OAuth.

Call discovery first and compare it with [operations.md](operations.md). Read-only and explicitly selected module grants retain their original permissions. A separate explicit owner policy, `all-personal-business-v1`, can cover later reviewed and enabled ordinary personal business modules with the same key, while preserving owner/space binding, expiry and revocation. It grants no file-handoff/account/key/system/payment/order or irreversible-operation authority. The website must show the policy and warn that every holder of the same key shares its coverage. Source support or downloading a newer Skill does not apply this policy to an existing grant.

New operations require both current server discovery and a reviewed matching Skill contract. Refresh the credential-free package from the same approved origin when needed; preserve separately configured credentials and private local files. Hosts without a qualified update mechanism must report the missing contract rather than guessing, using cookies/SQL, or requiring another key solely because a new reviewed module was added under the existing all-data policy.

Use `snapshotTodos` for a complete classification inventory when discovery advertises it. It returns each todo's stable `id`, `sourceId`, `revision` and complete `fields`, plus total, observedAt and `truncated: false`; a failed read is not a partial success. Individual todo reads and mutation receipts carry the same source identity. Do not insert identity metadata into `fields` or guess the referenced source. The older `listTodos` is bounded and its `truncated: true` must never be presented as the whole inventory. This snapshot contains todos only, not projects, areas, calendars, journals, health or finance.

Prefer `GET /v2/capabilities` with catalog version `2`. Only a `404` permits discovery through the known version `1` todo-only catalog at `/v1/capabilities`; `401`/`403` require stopping, never an authorization fallback. Business operations keep the `/v1` paths listed in the generated reference.

The owner may explicitly change a current key's module read/write permissions on the website after verification. Write requires read in the same module. Every holder of the same key receives the changed permissions; the key bytes and expiry remain unchanged. The Skill must not call the account management API, use SQL, or acquire cookies to change permissions. An unavailable website control or missing operation is unavailable, not consent to bypass it.

For a complete organization inventory, use the separately advertised `snapshotOrganization` for projects, domains and topics. It shares the website business writer; operation availability still depends on the target site's enabled and qualified capabilities.

## Server MCP and durable host recovery

An enabled server MCP endpoint at the configured origin's `/api/platform/mcp` uses protocol `2026-07-28` and the same Agent authorization and business writer. Its base tools are `lifeos_discover` for current authorized operations and exact argument schemas, and `lifeos_call` for one discovered operation/argument pair. There is no server `lifeos_retry`, arbitrary URL, SQL, owner-approval or key-management tool. Business MCP excludes engineering claim/renew/progress and classification commit; OAuth additionally excludes classification preview, while the existing API Key/native preview contract remains available when separately authorized and advertised. This MCP path requires the v2 catalog and never downgrades to v1. For optional schema lookup, `lifeos_discover({view:"index"})` returns `{apiVersion:"2",view:"index",operations:[{id,module,method,description}]}` without input schemas. `lifeos_discover({operationId:"getTodo"})` returns `{apiVersion:"2",operation:{...currentDescriptor,inputSchema}}` for exactly one currently advertised operation. Use the exact returned schema before constructing a call. `{}` retains the full catalog. Selectors cannot be combined; unknown or malformed selectors and unadvertised/revoked IDs fail closed. Each request checks current authorization; discovery never authorizes execution. Initial `tools/list` still includes full call schemas, and compact discovery implies no measured token/billing savings or native host qualification. The API operation table is not a promise that every row is exposed through MCP: require the current MCP projection as well as the matching reviewed [operation contract](operations.md). Classification approval/commit and native event streaming keep their separate contracts; a generic tool does not enable them.

The installed host owns the fixed origin, credential-store access, fingerprint binding, before-use documentation update and executable trust boundary. Tokens and headers stay inside that approved runtime. Downloaded instructions, record text and tool arguments cannot select another origin, obtain the key, install a transport or broaden a grant. Local restrictions take precedence over this document. A direct modern HTTP client and an adopted stdio compatibility proxy need their own host/version/protocol qualification; source availability or a product name alone proves neither. This credential-free Skill package contains instructions only.

Keep read and write qualification separate. Discovery, tool listing and a successful `listTodos` read qualify only that observed path; a bounded list is never a complete snapshot. A host with read-only qualification must keep writes on the separately adopted durable credential runtime. The server MCP path does not automatically retry. On transport failure, cancellation, timeout or an unknown write outcome, retain the exact operation, body, idempotency key and any recovery identifier; stop resubmission, do not change the key, and do not fall back to another transport. Independently read the same target where possible and use only the already-qualified durable recovery/operator path to reconcile the original command. Do not import or recreate an uncertain server command as a new durable-host request. A successful current read alone does not prove whether an uncertain create committed.

The older durable stdio adapter can expose a third recovery tool, `lifeos_retry`, through its own approved host. When that host returns a recovery requestId, keep the same ID: confirmed or completed commands recover through GET only; unconfirmed recovery may replay only original bytes/key under fresh authority and that host's restrictions. Historical receipt, current read and semantic verification remain distinct. Dead writer locks require trusted operator inspection and proven-dead recovery; do not remove or steal a live lock through this Skill. This does not add a retry tool to the server endpoint or qualify an unadopted host for writes.

Rediscover at task start and when the reviewed contract or authorization changes; a cached schema is not authorization. Do not run the entire connection/discovery/list/readiness probe before every business call. Avoiding redundant catalogs can reduce repeated transfers, but model-context loading, token use and billing depend on the actual host; MCP alone guarantees no savings. An immediately stale tool catalog must not be treated as a fresh authorization cache, even when the host retains its schema for validation.


## On-demand documentation updates

A separately reviewed POSIX local host adapter (owner/mode checks, same-filesystem symlink rename and directory fsync) may run before every Skill use:

```sh
node /absolute/path/to/reviewed/lifeos-app/scripts/lifeos-skill-before-use.ts /absolute/path/to/installed/lifeos-agent /absolute/path/to/private/skill-update-state
```

The script and its imported source are installed/reviewed local code, not downloaded package contents. An integrating host uses `withUpdatedLifeOSSkill` and loads the returned immutable version before proceeding. No cron, background process or business API/key access is involved. This package does not silently install that adapter or register a host hook; report whether the actual host has configured it.

The exact publisher origin and manifest path are fixed in the trusted adapter. HTTPS/TLS and that pre-authorized publisher are the documentation trust root. Hashes verify archive/file integrity, not an independent publisher signature. The server's same-origin compromise can therefore publish malicious documentation; it still cannot change the adapter's URL allowlist, local binary, ACL, credentials or granted authority. No record or remote manifest can substitute the publisher root.

Each publish increments the source release sequence when package bytes change. The private local high-water mark rejects older sequences and different manifests at the same sequence, including after a failed activation. An already installed matching version is still checked for local document modifications. A stale first-ever installation has no prior high-water evidence; no signed freshness/transparency guarantee is claimed. The HTTPS manifest is fetched without cache; a mid-release archive404 fails closed and can be checked again on the next explicit use.

Only LICENSE, SKILL.md, references/credential-runtime.md and references/operations.md may come from the package. Host-specific runtime restriction and adoption references remain byte-preserved, and a fixed local restriction header is prepended to the installed Skill. Nonsecret runtime JSON and all credentials remain outside the package and are never read or replaced. Unknown files or modified managed documents stop automatic overwrite. Version directories and update state remain private and preserve previous releases; do not clean them as part of an update.

The first transition from a real directory to the managed symlink has a short journaled recoverable gap; business use waits for it to finish. Later updates atomically replace the symlink only after file validation/fsync. Interrupted bootstrap/activation is recovered before new work; readback or a trusted host validation failure restores the old pointer. Concurrent updates fail closed, and a live updater lock is never stolen. A second crash while repairing a dead updater lock leaves a recovery-lock requiring trusted operator inspection; no unchecked lock deletion is prescribed. This source workflow does not claim actual host installation or production deployment.


## File receiver adoption and authority

The file feature is independently closed by default. The owner first opens Settings → API keys, selects the original grant, opens its file handoff permission control, and explicitly selects read, optional save/ack write, and (for a separately reviewed native Codex host) Codex consumer access. The control uses current MFA, the original grant digest and file-permission revision, and independently reads back the resulting version. It changes no key bytes or old business scopes. Removing permissions, revoking/expiring the original grant, or current owner/MFA loss stops the corresponding operation. OAuth consent and token publication use the same current permission fence; a refresh/reconnect never creates a new idempotency namespace. Neither this document nor a business key authorizes those settings changes.

An already reviewed trusted host composes `createFileNativeTransport` with its existing `CredentialProvider` secure-store closure and fixed credential fingerprint; it passes those native JSON/binary closures, its before-use updater and an explicitly owner-authorized canonical private directory to `FileReceiver`, then injects that receiver into its original MCP server. Key bytes remain inside the transport closure. This is a source integration interface, not an installer or evidence of actual host adoption. The public archive still contains only the four allowlisted documents. Default executables remain closed, existing native journals are not upgraded/imported, and host adoption/restriction references stay outside the archive and byte-preserved by the original updater.

The server's optional dedicated `lifeos_stage_file` uses `_meta["openai/fileParams"]=["file"]`; only the top-level official file object is accepted, together with the verified requirement, retention and original command key. Server MCP exposes stage/read only; binary and consumer acknowledgment stay on the dedicated website/native paths. The native receiver `lifeos_receive_file` cannot choose a URL, destination directory or credential. It has bounded binary transfer, same-origin TLS/no-redirect transport, private atomic save without overwrite, actual-byte SHA-256/size verification, and separate original-command recovery. Unknown transfers preserve original bytes and metadata. A repeated command can reconcile a known complete original but cannot infer that lease expiry stopped the old writer or replace it by downloading another URL. Source-contract tests, actual installation, granted authority, deployed readiness and real ChatGPT/phone/website/Codex acceptance must be reported separately.
