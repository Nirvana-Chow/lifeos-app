## Contract and implementation

- New record HTTP operations are GET `/v1/records/{journal|calendar|health|person|finance}/snapshot`, GET/PATCH `/v1/records/<type>/{id}` and POST `/v1/records/<type>`. Each type has separate snapshot/get/create/update IDs and `<type>:read` / `<type>:write` scopes. All use the native owner/space/source writer: `PersonalService` for the four ordinary types and `PersonalFinanceService` for finance. Snapshot/get/mutation results expose source identity and revisions. Finance snapshots retain manual-coverage semantics, integer-minor-unit totals and unknown account balances.
- Feedback adds GET `/v1/feedback/snapshot`, GET `/v1/feedback/{id}` and POST `/v1/feedback` through `RequirementSupportService`. The server assigns `agent-feedback`; no Agent review/conversion/archive/release-read operation is introduced.
- Ordinary record writes require all four `{title,text,occurredOn,personal}` fields. Explicit journal `personal:null` maps to its legacy native no-metadata representation. Finance writes require the complete existing nine-field `FinanceDraft`. All updates require `expectedRevision`; every write requires an idempotency key. Unknown body fields/query parameters are rejected. Owner, space, actor, confirmation and provenance come from the server binding.
- New `BusinessScope`/`OperationScope` types do not change `scopes.ts`, its original six-scope permission codec, key issuance or legacy Todo advertisements. In particular, `createTodo`/`updateTodo` still advertise only `todo:write`. Authority normalization explicitly branches on `all-personal-business-v1` and accepts new effective scopes only from exact allowed server-registry operations; legacy grants still use their unchanged codec. Legacy effective scopes may be retained in a policy actor even when a narrower operation list is supplied, preserving the existing policy contract; operation membership remains separately enforced.
- The new module flag is `LIFEOS_AGENT_PERSONAL_RECORDS=personal-records-v1`, and requires the existing explicit all-business policy flag. Original allowedTypes stay unchanged. Each native module gate is independent. Runtime only resolves/advertises exact enabled SQL registry operations after native readiness. Missing snapshot storage is unavailable. Default configurations and the old local todo credential runtime remain closed to these operations.
- Reads recheck current authority and operation availability before and after obtaining records. The original transaction fence runs before receipt access; the ordinary-record repository adapter additionally rechecks the same transaction-held grant before/after receipt read, write and receipt save. Finance reuses its native phase guards. Receipt recovery never skips revocation checks.
- `db/0017_personal_records_agent_operations.proposed.sql` only proposes23 new operation registrations with inherited `enabled=false`, behind exact database/owner/space and owning-role approval. It does not activate operations or policy, change keys/expiry/permissions, or replace0016 functions/digests. No SQL was applied.
- Skill source and the generated operation reference describe these contracts and the unchanged reviewed-runtime boundary. `skillReleaseSequence` remains the already-reserved `2026110502`. The final `skill-artifact-content.generated.ts` is deliberately left to root's one serial generation after integration; this branch must not be published as an independently complete Skill artifact.
