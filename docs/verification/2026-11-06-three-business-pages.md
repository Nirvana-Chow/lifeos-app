# Three business pages — integrated first versions

Continues the approved business-first plan, existing execution Issue30 and the sole unified-business-ui checklist. Owner acceptance and actual deployment remain separate from this source verification.

- `/personal/media`: books, films and series use the shared owner record editor, table and status board. State changes fetch the current record, retain complete fields, submit its expected revision through PersonalMutationSession and independently GET the saved record. Metadata lookup helpers are implemented separately; this page does not claim live Douban/IMDb synchronization.
- `/personal/career`: education, employment, achievements, resume versions and job opportunities share the same writer. The application board changes only opportunities; saved JD requirements can reference verified original facts. Resume preview uses saved facts and pins; no application is sent or qualification invented.
- `/personal/portfolio`: accounts, assets and investments have separate presentation and currency totals. The same owner record editor keeps unknown amounts unknown and validates dates and pinned account/asset references. This does not import a ledger or claim live market prices.
- Explicit pages retain the native owner MFA principal gate. Navigation requires verified storage and each exact server flag. The original five allowedTypes, existing Key grants and backend closed defaults are preserved. Generic generated Skill documents include all implemented Agent operations; actual advertisement still depends on grants, readiness and module gates.
- View containers scroll independently and preserve the toolbar. Custom record controls opt out of the shell's fallback button styling. Career columns scroll horizontally on small screens rather than forming a long stack. Existing ReUI table/modal/input components are retained; no new dependency is introduced.

Executed: eight new boundary tests, existing record tests, exact module navigation and owner-MFA tests; typecheck. Native Chrome ran six actual-component scenarios (1365px light / 390px dark for each module), using the real PersonalService/owner HTTP over an isolated internal MemoryPort fixture: create, independent GET, board-state persistence where applicable, edit, visibility hide/restore, reload, modal overflow and document overflow. Fixtures are internal checks, not owner records or website delivery. Screenshots were inspected; board title controls no longer inherit input-like fallback frames.

The first browser attempt caught a full Status object being passed as the narrow command binding; the fix passes only ownerId/spaceId. A subsequent six-scenario run passed. Existing people/health record tests were preserved; the new pure view tests are additive in personal-record-views.test.ts.
