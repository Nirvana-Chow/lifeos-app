## Implementation and integration seam

- Only `src/personal-finance/**`, its four named test files and this verification note are authored here. No shared router/config/Agent registry/Skill/OpenSpec/deployment file is changed; no dependency is added or installed.
- `PersonalFinanceService(repository,{ownerId,spaceId,enabled,writable})` provides status, complete snapshot, bounded list, get, create, update, mutate and history. Both gates default closed. Mutation input is `{spaceId,confirmed:true,fields:FinanceDraft,expectedRevision?}`; context is `{assertActor?,transactionGuard?}`. Root must pass verified storage/module/write authority rather than treating source code as runtime activation.
- Reuses `DraftService.mutate` and the existing finance schema/record/history/receipt transaction. The repository adapter limits access to the current owner, space and explicit immutable `source.original={marker:'personal-finance-manual-v1',spaceId,fields:<creation fields>}`. Old synthetic finance records cannot become manual records, be edited here or be selected as refund sources. Original keys are separately namespaced per space; replay returns the original revision/receipt. The actor and original-transaction grant guards run before receipt access and around writes/receipt save/final transaction return, so revocation throws through the existing rollback.
- Public records use `{id,type:'finance',spaceId,fields,source,revision,createdAt,updatedAt}`. Amounts remain positive integer minor units in CNY; totals use BigInt strings. Refunds reuse the locked same-owner/same-currency expense check. Transfers/repayments remain independent kinds and do not count as consumption. Account references/categories are derived from manual records, all account balances remain unknown, and coverage says `recorded-manual-transactions-only` with no external ledger connection.
- `handlePersonalFinance(request,{ownerId,baseURL,service?,assertOwner?,guard?,transactionGuard?})` (alias `handlePersonalFinanceRequest`) mounts after the shared session/owner boundary, before the generic personal router. GET `/api/platform/personal/finance/status`, `/snapshot`, `/` (optional `limit`), `/:id`, `/:id/history`; POST `/`; PATCH `/:id`. Website bearer authority is rejected. Responses are private/no-store. Root owns scoped Agent operations/discovery/Skill registration and must reuse the same service/transaction guard.
- `PersonalFinanceWorkbench({navigationGuard?})` uses existing ReUI DataGrid with native `fillWidth`, Button, Dialog and theme. It has honest empty state, input/list/detail/edit/history, refund picker, account/category view, exact decimal input, private-source coverage and unknown balances. It conceals content on hidden/changed identity and rechecks current owner/space before restoring it. Pending requests freeze the key/body and persist uncertainty before dispatch. A later rejection cannot undo an earlier unknown outcome. Only validated receipt plus independent GET plus final identity check plus verified recovery removal confirms saving. Definite CAS conflicts retain input for an explicit fresh-version recheck.

## Reuse and design evidence

- Existing `platform/domain.ts`, `platform/service.ts`, `platform/postgres.ts` and `finance-workbench` supplied finance semantics, refund locks, atomic writer, integer intake and conservative unknown-result recovery. The new adapter does not introduce another writer or schema.
- [PostgreSQL transaction documentation](https://www.postgresql.org/docs/18/tutorial-transactions.html) documents all-or-nothing rollback; this adapter delegates to the repository's existing transaction and rethrows guard failures. The documentation reference does not change the installed PostgreSQL target.
- [React Effect guidance](https://react.dev/reference/react/useEffect) supports ignoring obsolete responses and cleaning up effects. Generation tokens conceal stale data after identity/visibility changes. Existing React19.3.0/Next16.4.1/Node24.18.0 and the pinned lock are reused; OpenSpec CLI1.16.0 apply state was ready. No package update is attempted.
- UI Pro Max's broad finance design search did not match the existing product conventions; a focused form-label search was applicable. The implementation retains the established semantic palette/type/component system, visible labels and responsive density instead of introducing glass styling or new fonts.
