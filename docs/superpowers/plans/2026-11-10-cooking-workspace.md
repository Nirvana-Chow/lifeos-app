# Cooking Workspace Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development or superpowers:executing-plans. The unified-business-ui OpenSpec task file tracks execution.

**Goal:** Help the signed-in owner choose a dish and follow a verified recipe, then retain a private record of what they cooked.

**Architecture:** The first slice imports public text from a pinned HowToCook release, sends only catalog summaries to the browser and renders the chosen recipe from image-local data. A subsequent typed cooking record can use the existing personal record persistence, source identity, revisions and idempotency. Attachment bytes require a separately verified private storage path.

**Tech stack:** Current Next.js/React, LifeOS theme and controls, existing authentication and record services.

**Spec:** [Cooking workspace](../../../openspec/changes/unified-business-ui/specs/workspace-interface/spec.md#requirement-cooking-workspace) and [Issue #45](https://github.com/Nirvana-Chow/lifeos-app/issues/45).

The catalog slice adds no dependencies, third-party calls at runtime, cookies, grants, record writes or storage settings. Keep unknown times and amounts unknown. The [Cook Skill](https://github.com/YunYouJun/cook/blob/main/skills/cook/SKILL.md) informs the ingredient search workflow; the source is [HowToCook 1.6.0](https://github.com/Anduin2017/HowToCook/releases/tag/1.6.0). Store original attribution and license, exclude upstream media and render the textual recipe safely.

1. Catalog writer owns src/cooking/catalog.ts, catalog data, importer, attribution and catalog tests. Verify ten categories, 357 unique source paths, full sections and deterministic regeneration from the pinned release.
2. UI writer owns src/cooking/workspace.tsx and filter logic/styles/tests. Show a few initial suggestions, change the batch without early repeats, preserve category and ingredient filters when browsing, and render full instructions with a source link. Never present an ingredient match as proof all required items are available.
3. Integration writer owns app/personal/cooking, workspace navigation and route/browser qualification. Reuse the existing principal and PrivacyBoundary on catalog and direct recipe URLs. Test signed-out redirects, unknown recipe IDs, mobile layout and actual filter-to-detail interaction in light/dark. Independently review the combined slice, then follow the exact-source CI and release/readback gates.
4. Record slice: introduce typed date, dish, optional pinned recipe and notes with one owner writer, independent GET readback, isolated cross-owner and lost-response coverage. Scope discovery and Skill ship with the implemented write operation. Keep new live grants and schema activation behind their reviewed authorization boundary.
5. Photo slice: design a bounded private attachment store (Issue #16, #43); accept camera and photo library, make saved state depend on independent same-owner retrieval, and test refusal, retry, storage limits and recovery. No public object or third-party personal data processing. Real iPhone camera acceptance and owner review remain separate.

### Record candidate and production boundary

- Use the existing owner-only personal record writer, storing typed cooking payloads as existing inbox rows. No new personal-record table or general DB permission. Require an explicit actual date and title, allow empty notes, and allow a manual dish without a catalog reference. A selected recipe records the stable recipe ID and its exact pinned source link. Lists and exports must not expose cooking payloads when the module is closed. Keep source/revision and idempotent replay independent of the current catalog when a saved pin is unchanged.
- Gate the website writer separately with the reviewed cooking runtime flag. Reuse current origin, session, owner/space and storage checks. No credential upgrades, owner identity changes or general authentication changes. This checkout does not change the production runtime configuration.
- Scoped Agent operations require the existing all-business policy, exact capability registry/DB allowlist readiness and separately granted cooking read/write scopes. Legacy and explicit narrow keys retain their scope. Under the existing all-business policy, enabling the registered operations would also make them available to already authorized all-business keys; leave Agent registration disabled until that impact has been separately authorized or per-key enrollment has been reviewed. Ship HTTP registry, matching MCP source/tool schemas, Skill reference and proposed registration package together; the installed older local client remains unchanged. Deploy code that recognizes the new IDs before registering even disabled rows. Remove those rows and the new runtime flag before reverting to a release that does not recognize them.
- The history route does not save a browser-local substitute. Verify same-owner creation and readback, stale revision, unknown response recovery with the original key, unauthorized access, disabled route and refresh. Production activation is a separate, explicitly scoped step after the reviewed candidate and exact running source are identified.

### Photo design to qualify separately

Prefer same-origin private attachments with one photo per cooking record in the first version. On supported phones, offer the rear camera and a normal file picker. Show a local preview and retake action before sending; cancel leaves no server object. Re-encode the accepted image and verify the result independently to keep only supported image data and avoid preserving original location metadata. An unsupported image should fail clearly without losing the already saved text record.

Use the existing storage authority only after a bounded attachment design has been reviewed against #16 and #43. Compare a bounded DB-backed byte store (one consistent restore) with private object storage (different backup and consistency obligations); do not select a new service or extend production retention during source work. Bind every photo to the same owner/space/record as its metadata, refuse unknown record IDs and foreign reads, serve private no-store bytes, and keep picture grants separate from ordinary cooking text access. Cover exceeded quotas, failed upload, idempotent retry, logout, repeated GET, export/restore and actual phone capture before describing the feature as ready.
