# Business MCP parity

LO-AGENT-001 / LO-FILES-001 / personal-agent-foundation 11.1. The owner has explicitly requested current and future reviewed personal-business operations through MCP, using the same authorization and writer as the Agent API. Source, schema, runtime adoption, actual connection and owner acceptance remain separate gates.

At public2e3, the unique API registry contains67 JSON operations and one native SSE transport. HTTP MCP already supports60 operations and OAuth59; a static first-activation package only delegates journal/requirements. Broadening that package's five scope strings would neither remove duplicated operation lists nor authorize future reviewed business modules.

The chosen design keeps the official SDK and one executable API registry. An explicit MCP exposure annotation distinguishes reviewed business JSON operations, dedicated file handoff and internal/protected/engineering operations. MCP derives its supported operation IDs from those annotations. Exact local argument schemas, write receipts, original idempotency keys, current permission checks and independent same-ID GET remain mandatory. A newly reviewed operation ships its API/MCP/Skill contract and separately approved database registration together.

OAuth adds an explicit `personal-business:all` scope for the existing `all-personal-business-v1` policy. It requires explicit policy consent plus the selected original grant's same policy. Its effective operations are the intersection of the current original grant, enabled reviewed database operations, available modules and business MCP exposure. A new0025 migration extends the transaction-held OAuth fence; original0021 bytes and prior narrow-mode evidence remain unchanged. Existing explicit scopes never become this policy by inference, and unknown policy/scope combinations fail closed. Scope tokens are opaque server-defined strings under [RFC6749 section3.3](https://www.rfc-editor.org/rfc/rfc6749#section-3.3).

Account/security/configuration, execution claim/progress/terminal/deploy and native SSE remain outside business MCP. File persistence keeps its separate explicit permission, dedicated tool and original SQL fence. Protected classification commit keeps owner approval; OAuth classification preview remains closed until its original producer provenance is proven. Full-policy authorization does not bypass any of these boundaries.

Two dependent slices precede full-policy qualification: storage-item notes use the new operation's original revision/CAS/readback contract and a default-off0026 registration; the later login session change maps a stale management session to reauthentication while preserving the original signed OAuth query. Product auth/config/login/runtime remain owned by the login track.

The old basic1958/0021 actual-PG pass only covers its journal/requirements configuration. New policy SQL, runtime source, exact Caddy parsing, actual Native adoption, public HTTPS and real ChatGPT/Mac/phone/offline acceptance require their own evidence. No static/synthetic test is production acceptance.
